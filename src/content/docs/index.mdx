title: What is ClickHouse?
description: ClickHouse is an open-source database for analytical queries. Load large volumes of data, ask questions of it in SQL, and get answers in milliseconds.
---

ClickHouse is an open-source, column-oriented database for analytical queries: questions that scan and summarize many rows, such as "how many signups did we get per day last month, by country?" Teams use it for product analytics, logs and metrics, and dashboards that need answers in milliseconds to seconds.

With ClickHouse, you can:

- **Load large volumes of data** from files, other databases, or streams, in batches of thousands to millions of rows. See [How ClickHouse stores data](/clickhouse-guide/concepts/).
- **Query it in SQL**, with functions built for analytics, such as `uniq()` for distinct counts and `countIf()` for conditional counts. See the [Analysts guide](/clickhouse-guide/guides/analysts/).
- **Keep queries fast as data grows** by choosing how each table is sorted on disk. See the [Data engineers guide](/clickhouse-guide/guides/data-engineers/).
- **Run it where you need it**: on a laptop, on your own servers, or as a managed service.

## A query from start to finish

Here's how the parts fit together, using the dataset from the [Quickstart](/clickhouse-guide/quickstart/):

1. A data engineer creates an `events` table and chooses its **sorting key**, `(event_type, event_time)`, because most queries filter by event type.
2. They load one million events in a single `INSERT`. ClickHouse sorts the rows by that key and writes them to disk as one **part**.
3. An analyst asks how many purchases happened, and by how many users.
4. Because the table is sorted by `event_type`, ClickHouse reads only the blocks that hold purchases: 32 of the table's 123.
5. It reads only the two columns the query names and skips the other three. The answer comes back in milliseconds.

For why each of these steps is fast, see [How ClickHouse stores data](/clickhouse-guide/concepts/).

## When to use ClickHouse

ClickHouse is built for reading a few columns across many rows. It isn't built for frequent single-row updates.

| Use ClickHouse when | Example |
| --- | --- |
| You aggregate across many rows. | Daily active users for the last 90 days |
| Data is mostly appended, not updated. | Clickstream events, logs, metrics |
| People need answers quickly. | A dashboard that refreshes every few seconds |

| Use a row-oriented database when | Example |
| --- | --- |
| You update or delete single rows often. | Changing an order's status as it ships |
| You read whole rows by key. | Loading one customer's profile in an app |
| You need multi-row transactions. | Moving money between two accounts |

Many teams use both: a row-oriented database such as PostgreSQL runs the application, and ClickHouse answers the analytical questions.

## Choose how to run it

| Option | Good for |
| --- | --- |
| `clickhouse local` | Querying files on your laptop with no server at all |
| `clickhouse server` and `clickhouse client` | Learning how a real deployment behaves. The [Quickstart](/clickhouse-guide/quickstart/) uses this. |
| Docker image | An isolated environment you can throw away |
| ClickHouse Cloud | A managed service, with nothing to install |
