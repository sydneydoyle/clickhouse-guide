This guide takes you from nothing installed to a running ClickHouse server, a table of one million events, and the answer to a real question about them. It takes about 10 minutes.

You don't need to know ClickHouse to follow it. If you've written a `SELECT` with a `GROUP BY` before, you know enough SQL.

The steps follow one example: a product team wants to know which actions users take most on their website (page views, clicks, signups, or purchases), how many users take each one, and how long each takes.

<Aside title="Tested">
	The single-binary path was run end to end on macOS (Apple Silicon) with ClickHouse 26.12 on
	24 November 2026. The Docker path hasn't been tested yet. Surprises found along the way are on the
	[Troubleshooting](/clickhouse-guide/troubleshooting/) page.
</Aside>

## Before you begin

- macOS or Linux. On Windows, use WSL 2.
- A terminal.
- About 500 MB of free disk space. The ClickHouse program itself is about 180 MB.

## Set up ClickHouse and run a query

<Steps>

1. ### Install ClickHouse

   <Tabs syncKey="install">
   <TabItem label="Single binary">
   This downloads one `clickhouse` program into a new folder:

   ```sh
   mkdir clickhouse-quickstart && cd clickhouse-quickstart
   curl https://clickhouse.com/ | sh
   ```

   By default, the script also installs a second tool, `clickhousectl`, into `~/.local/bin`, and downloads a development build rather than a release. To change either, see [Troubleshooting](/clickhouse-guide/troubleshooting/#the-install-script-also-installs-clickhousectl-outside-your-folder).
   </TabItem>
   <TabItem label="Docker">
   ```sh
   docker run -d --name clickhouse-quickstart \
     -p 8123:8123 -p 9000:9000 \
     -e CLICKHOUSE_PASSWORD=changeme \
     --ulimit nofile=262144:262144 \
     clickhouse/clickhouse-server
   ```
   </TabItem>
   </Tabs>

2. ### Start the server

   <Tabs syncKey="install">
   <TabItem label="Single binary">
   ```sh
   ./clickhouse server
   ```
   The server prints a lot of log output, including some `<Warning>` lines. [That's expected](/clickhouse-guide/troubleshooting/#the-server-prints-warnings-on-startup). It also stores its data in folders it creates in the current directory, which is why you made a new folder in step 1.

   Leave the server running, and open a second terminal in the same folder for the next steps.
   </TabItem>
   <TabItem label="Docker">
   The container started the server in step 1. Check that it's running:
   ```sh
   docker ps --filter name=clickhouse-quickstart
   ```
   </TabItem>
   </Tabs>

3. ### Connect with the client

   <Tabs syncKey="install">
   <TabItem label="Single binary">
   ```sh
   ./clickhouse client
   ```
   </TabItem>
   <TabItem label="Docker">
   ```sh
   docker exec -it clickhouse-quickstart clickhouse-client --password changeme
   ```
   </TabItem>
   </Tabs>

   You'll see a prompt that ends in `:)`. From here on, type each SQL statement at that prompt.

4. ### Create a table

   Decide what you'll store and how you'll usually filter it. The product team stores one row per event, and most of their questions start with an event type, so the table is sorted by `event_type`, then by time:

   ```sql
   CREATE TABLE events
   (
       event_time  DateTime,
       user_id     UInt32,
       event_type  LowCardinality(String),
       page        String,
       duration_ms UInt32
   )
   ENGINE = MergeTree
   ORDER BY (event_type, event_time);
   ```

   | Part of the statement | What it decides |
   | --- | --- |
   | `ENGINE = MergeTree` | How the table is stored. Most tables use MergeTree. |
   | `ORDER BY (event_type, event_time)` | The **sorting key**: the order rows are stored in, which decides how much data a query can skip. |
   | `LowCardinality(String)` | Stores a column with few distinct values, like the four event types, more compactly. |

   For more on each choice, see [How ClickHouse stores data](/clickhouse-guide/concepts/).

5. ### Load sample data

   This generates one million synthetic events with the `numbers()` table function, so you don't need to download a dataset:

   ```sql
   INSERT INTO events
   SELECT
       now() - toIntervalSecond(rand(1) % 2592000)                AS event_time,
       rand(2) % 10000                                           AS user_id,
       ['page_view', 'click', 'signup', 'purchase'][1 + rand(3) % 4] AS event_type,
       concat('/page/', toString(rand(4) % 50))                  AS page,
       rand(5) % 5000                                            AS duration_ms
   FROM numbers(1000000);
   ```

   The events cover the last 30 days and 10,000 users.

   <Aside type="note">
   Each `rand()` call has a different argument (`rand(1)`, `rand(2)`, …). ClickHouse computes identical
   expressions in a query only once, so five plain `rand()` calls would put the same number in every
   column of a row. See [Troubleshooting](/clickhouse-guide/troubleshooting/#every-column-gets-the-same-random-value).
   </Aside>

6. ### Confirm the data loaded

   Before you query the data, check that it arrived as expected:

   ```sql
   SELECT count() FROM events;
   ```

   | Check | What to look for |
   | --- | --- |
   | Row count | `1000000` |
   | Insert errors | None. If the `INSERT` fails, the client prints an exception that starts with `Code:`. |

   If the count isn't `1000000`, drop the table with `DROP TABLE events`, repeat steps 4 and 5, and read any error the `INSERT` prints.

7. ### Answer the question

   Now ask the product team's question: for each type of event, how many events were there, how many users took that action, and how long did it take on average?

   ```sql
   SELECT
       event_type,
       count()               AS events,
       uniq(user_id)         AS users,
       round(avg(duration_ms)) AS avg_duration_ms
   FROM events
   GROUP BY event_type
   ORDER BY events DESC;
   ```

   You'll get four rows. Your numbers will be slightly different, because the data is random:

   ```
   ┌─event_type─┬─events─┬─users─┬─avg_duration_ms─┐
   │ signup     │ 250543 │ 10000 │            2499 │
   │ purchase   │ 250526 │ 10000 │            2498 │
   │ click      │ 249731 │ 10000 │            2498 │
   │ page_view  │ 249200 │ 10000 │            2500 │
   └────────────┴────────┴───────┴─────────────────┘
   ```

   The line under the result shows how many rows ClickHouse read and how long it took. In testing, this query took about 30 ms.

   `users` is 10,000 in every row because the synthetic data spreads a million events across 10,000 users, so every user has taken every action. Real data won't look this even.

8. ### Go further

   Once your first query works, choose what to try next. You might:

   - **Look at a time range:** Count events per day for the last week.

     ```sql
     SELECT toDate(event_time) AS day, count() AS events
     FROM events
     WHERE event_time >= now() - INTERVAL 7 DAY
     GROUP BY day
     ORDER BY day;
     ```

     You'll get eight rows, not seven, because the first and last days are only partly inside the 7-day window.

   - **Find the top pages:** List the ten most viewed pages.

     ```sql
     SELECT page, count() AS views
     FROM events
     WHERE event_type = 'page_view'
     GROUP BY page
     ORDER BY views DESC
     LIMIT 10;
     ```

   - **See what a query reads:** Follow [How ClickHouse stores data](/clickhouse-guide/concepts/#how-the-sorting-key-decides-what-a-query-reads) to see how the sorting key lets ClickHouse skip data.

   - **Load your own data:** Follow the [Data engineers guide](/clickhouse-guide/guides/data-engineers/) to load a CSV file.

   You don't need to do all of these. Pick the one closest to your work.

</Steps>

## Clean up

When you're finished, delete the table:

```sql
DROP TABLE events;
```

Then stop the server:

<Tabs syncKey="install">
<TabItem label="Single binary">
Press <kbd>Ctrl</kbd>+<kbd>C</kbd> in the server's terminal, then delete the `clickhouse-quickstart` folder.
</TabItem>
<TabItem label="Docker">
```sh
docker rm -f clickhouse-quickstart
```
</TabItem>
</Tabs>
